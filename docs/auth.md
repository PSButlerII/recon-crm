# Recon CRM owner authentication

Recon CRM uses simple single-owner authentication: a password is verified on the server and a signed HTTP-only session cookie keeps the owner signed in. This is intentionally not Auth.js/NextAuth and does not create database `User` or `Session` tables yet.

## Required environment variables

| Variable | Required | Description |
| --- | --- | --- |
| `CRM_AUTH_PASSWORD_HASH` | Yes | Password hash used by `/api/auth/login`. Prefer the `pbkdf2:<iterations>:<salt>:<hex>` format generated by `npm run auth:hash`. |
| `CRM_SESSION_SECRET` | Yes | Random secret used to sign session cookies. Use a high-entropy value and keep it private. |
| `CRM_SESSION_COOKIE_NAME` | No | Cookie name. Defaults to `recon_crm_session`. |
| `CRM_SESSION_TTL_SECONDS` | No | Session lifetime in seconds. Defaults to `28800` seconds (8 hours). |

If either required variable is missing, CRM pages redirect to `/login` and protected CRM API routes return `401`.

## Generate `CRM_SESSION_SECRET`

Generate a 32-byte random secret:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Set the result as `CRM_SESSION_SECRET` in your local `.env` file or production environment.

## Generate `CRM_AUTH_PASSWORD_HASH`

Use the included helper:

```bash
npm run auth:hash
```

The script prompts for the owner password and prints a value like:

```text
pbkdf2:310000:<salt>:<hash>
```

Set the full printed value as `CRM_AUTH_PASSWORD_HASH`.

For non-interactive local setup, you can pass the password as an argument:

```bash
npm run auth:hash -- "replace-with-owner-password"
```

Avoid using the argument form in shared terminals or CI logs because shell history may retain the password.

## Session TTL and cookie notes

- Sessions are stateless and signed with `CRM_SESSION_SECRET`.
- Session cookies are HTTP-only and use `SameSite=Lax`.
- Cookies are marked `Secure` when `NODE_ENV=production`, so production deployments must serve the app over HTTPS.
- `CRM_SESSION_TTL_SECONDS` controls both the cookie `maxAge` and signed token expiration.
- Rotating `CRM_SESSION_SECRET` invalidates existing sessions immediately.

## Local testing checklist

1. Set `CRM_SESSION_SECRET` and `CRM_AUTH_PASSWORD_HASH` locally.
2. Run `npm run dev`.
3. Open `/login` and confirm it renders without the CRM sidebar.
4. Open `/` while logged out and confirm it redirects to `/login`.
5. Submit an incorrect password and confirm login fails.
6. Submit the correct password and confirm the CRM workspace loads.
7. Refresh the CRM page and confirm the session remains valid until the TTL expires.
8. Click **Logout** in the sidebar and confirm the app returns to `/login`.
9. Request a protected API route while logged out, for example `/api/clients`, and confirm it returns `401` JSON.
10. Run `npm run lint` and `npm run build` before deploying.

## Production checklist

- Store auth environment variables in the deployment platform's secret manager.
- Use HTTPS so the production `Secure` cookie is accepted by browsers.
- Keep `/login` public; keep CRM pages inside `app/(crm)` so the protected layout applies.
- Keep protected API routes using `requireApiAuth` unless a route is intentionally public.
- Do not expose the Debug page in production navigation.
